# Fluent v0.8.0

Fluent 0.8.0 expands the dashboard into a place to inspect Work, watch workers,
and run supported local actions. It also keeps navigation responsive during
source reads and adds explicit approval for Tester commands that need access
to the macOS process table.

## Upgrade an existing project

Stop the Fluent scheduler if it is running, run `fluent update`, and confirm
that `fluent version` reports 0.8.0. Restart the scheduler if you use it. Keep
your project's `.fluent` directory and managed worktrees; you do not need to
run `fluent init` again. Run `fluent status` to inspect unfinished work and its
next available action.

For Claude session recovery from v0.6.0, or a transition from v0.5.0 with a
shared scheduler, follow the [transition procedure](next.md). Once a newer
binary writes Work records, continue with a compatible version; older binaries
may refuse to change those records.

## Inspect Work and workers in the dashboard

Run `fluent dashboard` from a checkout. It includes projects already registered
with the scheduler; repeat `--project /path/to/checkout` to include additional
checkouts without registering them.

The dashboard opens on Current Work. Tab and Shift+Tab cycle through Current,
Needs you, Running, Ready, Waiting, and History. Each list row represents one
Work Item. Enter or Right opens its overview, which shows its condition, next
action, and workers. Select a worker and press Enter for its details. Esc or
Left returns one level while retaining selection. PageUp and PageDown move
both the list page and selection; on detail pages they scroll the content.
The footer and `?` help show controls for the current page.

The dashboard draws before its first Work read and accepts navigation while
local snapshots load. Failed or overdue sources retain their last successful
snapshot with a warning. Source health shows healthy, failed, and overdue
counts; press `e` for read diagnostics and last successful read times. Routine
polling stays quiet, while initial and requested reads show activity after a
short delay.

## Run supported local actions

Press `a` in a Work Item overview to inspect available actions. Eligible Work
offers Run Attempt, Show Candidate, or Land Candidate, with the command and
source checkout visible. Run Attempt and Land Candidate require a fresh state
check and explicit `y` confirmation. Enter does not confirm. Show Candidate
is read-only and needs no confirmation.

Local commands run in the foreground with live output. After exit or Ctrl-C,
the dashboard returns, reports the process result, and refreshes Work state.
The open detail page stays tied to the same Work Item even if that refresh
moves it to another view. SSH sources offer commands to copy and run yourself;
the dashboard does not execute these actions remotely.

## Watch native terminals

Press `t` on a native worker to observe its terminal, `i` to take Control,
`Ctrl-]` to return input to dashboard navigation, and `f` for full-screen
attachment. Literal terminal input appears in help only while Control owns
input. Native Codex startup and display handling include fixes for denied
probe retries and terminal backpressure. See the
[dashboard guide](../../README.md#watch-work-across-projects) for controls and
the [SSH guide](../../docs/ssh-agent-sources.md) for remote prerequisites.

## Approve Tester process-table access explicitly

A command in `.fluent/tester.yaml` can request
`permissions: [process-table-read]`. The request grants no access by itself.
From the clean candidate checkout, use `fluent tester permissions show` to
inspect the exact candidate and command index, then `approve` with its request
digest. Approval does not start or resume a Tester. A changed commit, checkout,
Tester configuration, extractor, or permission policy requires fresh approval.
Use `fluent tester permissions revoke <approval-id>` to stop later launches.

This capability exposes host-wide process metadata to the approved command and
its descendants. Other commands and agent roles keep their default sandbox.
See the [Tester permission instructions](../../README.md#how-fluent-builds-it)
for the command syntax and exposure limits.

## Preserve release verification

Ordinary Work runs the canonical Rust and shell suites in `.fluent/tester.yaml`.
Release-only host checks remain separate in `.fluent/release-host.yaml`.
Publication requires accepted evidence for all seven checks on the exact
candidate, ordinary reviews, the complete final Tester, and successful Learning.
The release script verifies these gates before publishing macOS binaries and
their checksums. Moving host checks out of ordinary Work does not waive them
for a release.
